# AirBand Updater and Installer

## Premises

A plugin binary executes inside a host process that owns its address space and decides when the binary is loaded and unloaded. The plugin therefore cannot replace itself, and on Windows the operating system keeps a loaded module locked against replacement. Installing and updating are consequently acts of a separate program that runs while hosts may be open, and their effect becomes visible when a host next starts or rescans its plugins.

The audio callback is held to a realtime contract that the RealtimeSanitizer gate enforces: processBlock and setParameters never allocate, lock or block. Network access and file replacement belong to a different execution context, so all of that logic lives in its own executable. The plugin carries no updater code and opens no connection of its own.

A release is the unit of distribution. One version number in CMakeLists.txt flows into the bundle metadata, the macOS installer package, the Windows installer and the release tag, and every release carries four assets under fixed names: AirBand-macOS.zip, AirBand-macOS.pkg, AirBand-windows.zip and AirBand-windows-setup.exe. The download buttons in the README resolve through the latest release by those names. The updater consumes the same contract, so publishing a release is the single act that makes a new version available both to a person clicking a button and to the updater.

Installation scope is a property of the machine's existing state. The macOS package writes to the shared Library folder, the macOS archive is installed into the account's own Library, and the Windows installer writes to the shared Common Files folder. A host that finds the plugin in two folders lists it twice, so an update modifies the scope that already holds the plugin, a first install on macOS uses the account's own folders because they need no administrator rights, and an installation present in both scopes is reported as a conflict for the user to resolve.

Releases carry an ad-hoc code seal and are not notarized, so the available basis for trust is the SHA-256 digest that GitHub publishes with every asset. A digest obtained over HTTPS from the release API establishes that the bytes received are the bytes that were published, including after truncation or a partial upload. Establishing that the publisher is the author requires a signing key pinned inside the updater, which is listed below as an open decision. An asset that lacks a published digest is therefore treated as unavailable.

Finally, the plugin that works today must keep working. A failed installation leaves the previous installation intact.

## Mechanism

The updater reads the installed version from the Info.plist of each bundle and takes the oldest present version as the installed version, so that a half-finished update is completed rather than skipped. It compares that version with the version in the latest release's tag. A version is three numeric components compared numerically, so 1.10.0 follows 1.9.9. Four outcomes follow. Nothing installed leads to an install, an older version leads to an update, an equal version leads to no action, and a newer version, which can only be a development build, leads to a refusal that the force option overrides. The same option permits reinstalling an equal version.

The scope comes from where the plugin already is, or from an explicit option, and the asset name follows from platform and scope. The asset is streamed to a temporary file, checked against the size and digest that the release lists for it, and deleted on any mismatch. On macOS the user-scope archive is unpacked with ditto into a staging directory on the same volume as the plugin folders, so that the final step is a rename. In staging, each bundle must carry a code seal that codesign verifies in strict mode and a bundle version equal to the release version, and only then is any installed file touched. Each installed bundle moves into the staging area, the new bundle takes its place, and the installed result is verified again with the same two checks. When any step fails, the bundles already swapped return to their previous state and the staging directory is removed. A host that has the old binary loaded keeps running it, because the rename gives the new bundle a new file identity, and the updater reports such hosts so that the user knows a restart is needed.

Three commands expose this. Status prints each bundle location with its version. Check adds the latest release and the decision, and exits with status 10 when an install or update is available so that other tools can branch on it. Install carries out the steps above, with a dry-run option that stops before the download. A prefix option redirects every path to a scratch directory and names the one place to look, which makes the whole sequence testable without touching the real plugin folders.

## Operating environment

The macOS target is the universal arm64 and x86_64 build for macOS 11 and later, and a user-scope install runs without elevation. The Windows target is 64-bit Windows, where the setup program elevates itself because it writes the shared folder. A run costs one unauthenticated request to the GitHub API, within GitHub's limit of sixty such requests per hour per address, and one download of about six megabytes on macOS or four on Windows. The download streams to disk in 64 KiB blocks and is hashed from the file, so memory use is independent of asset size. The updater keeps no state between runs: each run derives its decision afresh from the plugin folders and the release, so running it twice has the same effect as running it once. When the network is unreachable the run ends with an error that names the failed request and changes nothing.

## Structure and status

The library airband_updater_core, built over juce_core and juce_cryptography, holds version and release parsing, the platform contract of asset names and install locations, inspection of the installed state, the decision, digest verification, a download-and-verify routine written against an abstract fetcher, and on macOS the installer. The executable AirBand_Updater adds the real HTTPS fetcher and the command line. AirBand_UpdaterTests exercises the library with 82 checks, using a fake network for the download path, scratch directories for inspection, and real ad-hoc-signed bundle archives for the installer. The installer cases cover a fresh install, an upgrade, an archive that does not match the release, a tampered code seal, and an unwritable Components folder that forces a rollback after the VST3 has already been replaced. The rollback check was confirmed to fail when the rollback is disabled.

The command line was run against the live v1.3.2 release. It reported the installed 1.3.2 as current and left the plugin folder unchanged, and it installed the published archive into a scratch prefix with binaries identical to the release hashes, after which a second run found nothing to do.

Three parts are specified here and await implementation, and the command line stops with an error that names the asset URL where they apply. Windows version detection reads the DisplayVersion value under the uninstall registry key that the Inno Setup script's AppId produces, which is {28B284A1-659F-4A78-8BD0-ABD96BAEABC0}_is1. Windows installation runs the verified setup program with the silent flags that the Windows workflow already exercises. System-scope installation on macOS runs the package and needs administrator authorization. The Windows build of the updater targets has not yet been compiled, so adding them to the Windows workflow is the first step of that work.

Two decisions remain open. The first is authenticity: a signing key pinned in the updater and a signed manifest published with each release would extend trust from the integrity of the bytes to the identity of the publisher. The second is how a person obtains the updater itself, either as a fifth release asset carrying its own seal or through the existing installers.
